## 1. 项目愿景、定位与成功标准

### 1.1 一句话定位

为全球用户提供**可信、可解释、能持续调整**的 AI 私人训练与身体管理平台，把训练、营养、身体变化与恢复信息连接成闭环。

### 1.2 产品核心闭环

**建档 → 生成初始训练/营养目标 → 每日执行与记录 → 每周回顾 → AI 提供解释和调整建议 → 用户确认 → 持续追踪。**

用户需要能够回答四个问题：

- **今天练什么？** 根据目标、训练水平、器械、训练时间和恢复反馈给出可执行计划。
- **今天吃多少？** 查看目标热量及蛋白质/碳水/脂肪，记录实际摄入；热量和运动消耗为估计值。
- **身体有没有变化？** 查看体重、围度、进度照片、训练表现趋势。
- **下周怎么调整？** 系统综合真实记录提出可解释、可否决的建议。

### 1.3 首发产品边界（已确认）

**首发包含：** 训练、营养、身体追踪、AI 教练，含中英双语与 Android/iOS 交付要求。  
**后置：** 复杂视频姿态识别、职业健美备赛专项系统、较完整的户外运动/GPS社交、专业康复协作。  
**禁止首发承诺：** AI 可确诊疾病、术后自动开康复处方、摄像头能百分之百判断动作安全、食物照片能精确算出热量、算法能保证某一训练或减重结果。

### 1.4 首发用户与定位

| 用户 | 典型需求 | 首发方案 |
| --- | --- | --- |
| 健身新手 | 不知从哪里开始、怕练错 | 简洁建档、循序渐进计划、动作说明、基础饮食引导 |
| 普通健身爱好者 | 增肌/减脂/减脂保肌 | 训练记录、营养目标、体重/照片与趋势 |
| 有经验的力量训练者 | 比较强度、容量、恢复 | RIR/RPE、组次重量、历史趋势、建议型负荷调整 |
| 职业健美与备赛选手 | 周期化训练、备赛饮食、体型追踪 | 首发可用基础记录；专用工作流在 R07 后置 |
| 跑步、骑行、徒步用户 | 户外运动与活动量 | 首发可手动记录基本活动；GPS、高级运动分析后置 |
| 术后康复人群 | 受监督的康复训练 | 首发仅提供风险识别和专业就医提示；不自动开具康复处方 |

### 1.5 首发成效指标（上线前定义并迭代）

- **产品可用性：** 核心流程在真实 Android 与 iOS 测试设备上通过。
- **记录可信度：** 训练、饮食、体重记录保存后可查、可更正、可导出，不发生意外丢失/重复写入。
- **首周体验：** 新用户能在可接受时间内完成建档并记录至少一次训练和一餐（具体数值通过用户测试设定，不凭空承诺）。
- **安全：** 服务端不泄漏 API 密钥，关键表有用户级鉴权与 RLS，敏感照片只向有权用户开放。
- **稳定：** 崩溃、同步冲突、AI 调用失败、断网重试均有可观察的处理路径。
- **商业判断：** 真实测试用户的留存、记录完成率、会员转化意愿达到未来拟定门槛后再扩大获客。

## 3. 核心使用流程与页面信息架构

### 3.1 首次使用

1. 选择语言、地区/单位；阅读隐私说明与必要同意项。
2. 登录/注册（开发早期可允许不使用真实账号的测试模式，发布范围需另行确认）。
3. 智能建档：基本信息 → 健身目标 → 经验与历史指标 → 可用器械/时间 → 身体限制与警示。
4. 展示计划依据、注意事项及可能不适用的情形；用户确认初始计划和目标。
5. 进入首页，开始记录训练、饮食及身体数据。

### 3.2 五个底部导航

- **首页 Home：** 今日训练、营养目标进度、恢复反馈、最近趋势、AI 提醒。
- **训练 Workout：** 训练日历/计划、动作库、开始训练、每组记录、计时、历史与负荷建议。
- **营养 Nutrition：** 日志、食物搜索、热量/宏量营养素、常用餐食；后期加入拍照识别。
- **进度 Progress：** 体重/围度、进度照片对比、训练统计、周报。
- **我的 Profile：** 身体档案、目标、语言/单位、隐私、导出/删除、账号、订阅。

**AI 教练**使用全局入口，不占第六个底部 Tab；后续专业模式放在二级页面。

### 3.3 关键用户故事

- 作为新手，我输入每周有 3 天、每次 45 分钟和现有器械，得到可以理解的入门训练计划。
- 作为训练者，我完成深蹲 4 组，记录各组重量、次数及 RIR；重开 APP 后记录不消失。
- 作为减脂用户，我记录一餐食物及份量，知道自己与今日目标的差额，不把消耗热量误当精确值。
- 作为备赛意向用户，我可按日期上传多张进度照片并掌握其删除权限；专业备赛工具将在后续开放。
- 作为 AI 教练用户，我可以查看为何建议调整训练量或饮食目标，确认或拒绝调整，不影响原始日志。

## 4. 功能规格与验收标准

### 4.1 F01 智能建档（P0）

**必需字段：** `user_id`、建档时间、年龄或出生年月（数据最小化）、身高、体重、单位、目标、训练经验、每周训练天数、单次时长、运动场景、器械清单、当前限制/疼痛或术后风险提示、用户是否同意使用相关数据生成建议。  
**可选字段：** 历史训练指标（例如深蹲/卧推/硬拉）、围度、活动水平、训练偏好。生理相关字段只有明确必要时询问，并解释用途。

**规则：** 不因缺少历史力量数据阻止新手使用；缺乏关键安全信息时不得生成高风险训练建议。应支持用户后期编辑建档并记录版本。

**验收：** 新手/资深用户均能完成；必填验证、单位转换、中英界面无误；未填与数值零可区分。

### 4.2 F02 训练计划（P0）

**目标：** 增肌、减脂、减脂保肌、综合体能。  
**输入：** 目标、经验、可用时间/器械、运动限制、上次表现、恢复信息。  
**输出：** 周计划、每次动作顺序、动作名称及替代动作、组数/次数范围、休息时间、建议强度（如 RIR/RPE）、热身及注意事项。  
**限制：** 建议应考虑合理渐进、恢复间隔、使用者经验；未知 1RM 时不能将估算值当测量值。

**验收：** 2/3/4 天训练频率及居家/健身房场景生成适配内容；无相应器械时有替代动作；用户可调整/接受计划，修改留痕。

### 4.3 F03 训练记录（P0）

**每次训练：** `session_id`、计划引用、开始/结束时间、动作/组次序列、重量、次数、RIR/RPE（可选）、备注、完成状态。  
**交互：** 大按钮/快速勾选、上一组数据带入但需用户确认、组间计时、编辑和撤销。  
**离线：** 无网络也能新增/编辑本地训练记录并正常查看。

**验收：** 关闭/重启 APP 后数据仍在；重复点击不产生重复组；跨日期、单位换算正确；历史数据不可被 AI 静默更改。

### 4.4 F04 恢复和负荷建议（P0）

**输入：** 训练表现、主观疲劳、睡眠、肌肉酸痛、休息天数、近期训练量；缺失项不得虚构。  
**输出：** 下次训练的可解释建议，如保持、适度增加、降低或推迟训练；明确是建议而非强制处方。  
**风险：** 疼痛、术后、明显功能异常等触发更谨慎提示/停止自动建议。

**验收：** 同一输入产生可追溯建议；低信心/高风险时主动说明；用户未确认前不修改正式训练计划。

### 4.5 F05 营养（P0）

**包含：** 用户目标、每日目标热量和三大营养素、食物手动搜索/创建、单位和份量、餐次、常用餐食、日期日志、编辑/删除、能量及营养合计。  
**计算：** 初始热量只作估算，逐步依据足够的连续体重与摄入记录复核。能量消耗须标明算法或设备估计，不能当成精确数值，不默认将估算运动消耗 100% 加回饮食额度。  
**食物数据：** 食品数据来源和地区差异需要管理；用户录入与数据库值要注明来源。

**验收：** 可记录早餐/午餐/晚餐；修改份量后合计更新；删除餐食会更新合计；输入异常有校验；中英文单位/食物查询策略可说明。

### 4.6 F06 身体变化（P0）

**内容：** 体重、腰围等围度、记录时间、单位、历史曲线、不同日期进度照片，支持同角度对比。  
**隐私：** 默认私密，不自动公开；照片存储与下载鉴权；允许选择单张删除和导出。不得把身体图像上传给未知第三方。  
**表现：** 缺失数据不填造；避免因单日体重波动立即给激进减重建议。

**验收：** 可按日期记录/编辑；图表正确；进度照片只由本人或经明确授权的角色访问；删除操作有明确反馈。

### 4.7 F07 AI 教练（P0）

**能力：** 回答训练和营养基本问题；在用户授权范围内引用真实记录、解释计划、提出周度建议、建议训练调整。  
**上下文：** 仅检索最小必要数据，报告使用哪些数据及哪些缺失。  
**动作权限：** AI 输出仅是建议对象，业务层进行安全校验，用户明确确认后再生成新的计划版本；不能直接写/删原始日志。  
**故障：** 请求超时/配额耗尽/模型不可用要有可理解错误和非 AI 的基本记录功能。

**验收：** 不能跨用户读取数据；禁止客户端明文密钥；高风险话题有恰当限制；AI 建议具可追溯日志与确认状态。

### 4.8 F08 食物照片识别（P1）

**流程：** 拍照/选图 → 客户端说明使用用途 → 后端处理 → 返回候选食物/估算份量/热量区间 → 用户修改并确认 → 存入日志。  
**限制：** 不承诺对烹饪油、隐藏原料及重量的准确识别；显示不确定性；支持手动添加。

**验收：** 用户可以纠正误识别；没有确认不生成饮食记录；上传失败或权限拒绝时可退回手动输入。

### 4.9 F09 周报（P1）

**内容：** 周训练完成率、训练量趋势、体重趋势、营养记录覆盖率、恢复反馈、下一阶段建议。  
**原则：** 记录不足时标注“数据不足”，不猜测训练量、热量或体脂变化。

**验收：** 每个指标可回溯来源；同一报告可查看数据区间、版本和创建时间；调整方案需用户确认。

## 5. 安全、健康风险与用户保护

1. 产品是一般运动/健康管理工具，**不替代医生、物理治疗师或注册营养专业人员的诊断与治疗**。
2. 存在术后恢复、急性损伤、持续加重的疼痛、严重疾病相关限制等风险时，首发不自动处方康复训练；提示遵循专业人员的个体化方案。
3. 可能涉及未成年人、孕期、进食障碍相关担忧、极端减重/脱水等场景时采取更谨慎的产品策略，不能照搬普通成年人营养算法；后续上线前做专门安全审查。
4. 训练建议要说明强度及替代动作，不以“不痛就没事”等绝对性判断代替健康评估。
5. 职业健美备赛后期模块不提供药物滥用、危险脱水或极端低热量做法的自动指导。
6. 视频姿态分析后期仅分析画面可见的有限信息；不能通过单一手机视角宣称可以准确衡量全部关节受力或诊断伤病。
7. AI 输出不得编造历史训练数据、食物摄入、体重及健康状态。
8. 应有清晰免责声明，但**免责声明不能代替实际风控逻辑**；高风险触发需要在程序里明确拦截或降级。

## 6. 技术架构（已确认，不随意更换）

| 层次 | 选型 | 职责 |
| --- | --- | --- |
| 客户端 | React Native + Expo + TypeScript | Android/iOS 交互与状态管理 |
| 路由 | Expo Router | 页面组织和导航 |
| 本地存储 | SQLite（Expo 兼容实现） | 训练与可离线记录；保留原始日志 |
| 身份认证 | Supabase Auth | 用户登录与账号管理 |
| 云数据库 | Supabase Postgres | 用户授权的同步数据、计划、营养、报告等 |
| 文件存储 | Supabase Storage 私有桶 | 身体照片等敏感附件 |
| AI 服务 | 受认证的服务端接口（如 Supabase Edge Functions） | 调用模型、鉴权、限流、日志与安全校验 |
| 代码管理 | Git + GitHub **Private** 仓库 | 版本历史、跨电脑恢复、协作 |
| 测试 | 单元/集成测试 + Android/iOS 实机 | 功能、数据、账号和发布验证 |
| 持续构建 | Expo EAS（发布阶段） | 移动端构建与交付 |

### 6.1 设计要求

- **Offline-first：** 训练时不依赖稳定网络；记录先本地持久化，再按策略同步。
- **数据隔离：** Supabase 数据按 `user_id` 隔离，所有含用户数据的表启用并测试 Row Level Security (RLS)。
- **安全密钥：** AI Provider Key、Supabase Service Role Key 等只在受控服务端；客户端仅使用公开且权限受限的配置项。
- **认证和传输：** HTTPS、访问控制、最小权限、服务器端验证、AI 调用配额及成本限制。
- **同步：** 设计稳定记录 ID、更新时间、删除标记、幂等上传、冲突处理和失败重试；不能用全表覆盖替代同步。
- **迁移：** SQLite schema version + migration，数据库升级前备份与测试，不丢旧日志。
- **审计：** 记录 AI 建议生成时间、输入来源摘要、模型版本、用户是否接受；不在日志输出完整敏感原文。
- **国际化：** 中英文文案不硬编码，支持 kg/lb、cm/in、kcal、地区时间与时区正确性。
- **隐私与合规：** 收集最少必要信息；提供数据导出/删除、撤回可选授权、清晰的数据留存说明。全球上市需按实际目标地区审查 GDPR 等适用规则及商店健康数据政策，不假定一个政策覆盖所有国家。
- **订阅：** 后期按应用商店要求接入合规订阅方案；不得在 R01/R02 接入未经确认的支付系统。

- 任何服务端密钥、访问令牌、真实凭据或可识别的用户隐私数据。

## 14. Markdown 文件保存到 Windows 的操作说明

1. 从 ChatGPT 下载 `PROJECT_MASTER_PLAN.md` 到电脑的“下载”文件夹。
2. 打开文件资源管理器（`Win + E`）。
3. 进入 `C:\Development`；若没有则创建 `Development` 文件夹。
4. 如果项目文件夹还未创建，可先建立 `global-fitness-app`；若已有文件夹，进入原文件夹，不另建同名目录。
5. 在 `global-fitness-app` 中创建 `docs` 文件夹。
6. 将下载的 `PROJECT_MASTER_PLAN.md` **复制**到 `C:\Development\global-fitness-app\docs\PROJECT_MASTER_PLAN.md`。
7. 在资源管理器“查看”中开启文件扩展名，核对文件名确实是 `.md`，而不是 `.md.txt`。
8. 用 VS Code 打开项目文件夹，点击 `docs/PROJECT_MASTER_PLAN.md` 检查正文是否完整。
9. **文件在本地不等于已备份：** R01 的 GitHub Private 仓库和首次成功推送仍须单独完成。
